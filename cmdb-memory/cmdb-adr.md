# CMDB 平台架构决策记录（ADR）

- 版本：v1.0
- 日期：2026-01-12

## ADR-001: 编程语言选择 Go

- 状态：已接受
- 背景：需要选择核心后端实现语言以兼容现有巡检工具与运维生态。
- 决策：选用 Go 作为主要编程语言。
- 理由：现有巡检工具100%用Go实现可直接复用、单二进制部署无依赖、goroutine并发优势、云原生运维工具事实标准。
- 后果：后端统一为 Go 技术栈，降低复用成本与部署复杂度。

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| Go | 复用现有代码、单二进制部署、并发强、运维生态成熟 | 学习曲线中等 | 采用 |
| Python | 生态广泛 | GIL限制并发性能 | 不采用 |
| Java | 企业生态成熟 | 需JVM、部署复杂 | 不采用 |
| Node.js | 前后端同语 | 需运行时、稳定性受限 | 不采用 |

## ADR-002: 数据库选择 PostgreSQL

- 状态：已接受
- 背景：资产标签与关系模型需要强一致性与灵活结构化存储。
- 决策：选用 PostgreSQL 作为主数据库。
- 理由：JSONB原生索引支持资产标签、严格数据完整性约束、与Grafana/N9E运维生态兼容。
- 后果：依赖 PostgreSQL 的高级特性（JSONB/索引/约束）。

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| PostgreSQL | JSONB索引、强一致性、生态兼容 | 运维成本略高 | 采用 |
| MySQL | 普及度高 | JSON索引能力弱、默认宽松模式 | 不采用 |

## ADR-003: 代码管理采用 Monorepo + Go Workspace

- 状态：已接受
- 背景：前后端与共享库需要一致版本控制与原子提交。
- 决策：采用 Monorepo + Go Workspace 组织代码。
- 理由：原子性提交（前后端+共享库一次commit）、无需replace指令、单人开发效率高。
- 后果：统一仓库管理，简化依赖与版本对齐。

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| Monorepo + Go Workspace | 原子提交、依赖一致、简化开发 | 仓库体积增长 | 采用 |
| 多仓库 | 责任清晰 | 版本对齐成本高 | 不采用 |

**结构约定**
- `pkg/`：共享库
- `apps/inspect-cli`：巡检命令行
- `apps/cmdb-server`：CMDB 服务端
- `web/`：前端

## ADR-004: Web框架选择 Gin

- 状态：已接受
- 背景：需要成熟稳定的高性能 Web 框架支撑 API 服务。
- 决策：选用 Gin 作为 Web 框架。
- 理由：高性能、中间件生态丰富、文档完善、Go社区最流行。
- 后果：中间件与路由体系基于 Gin 构建。

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| Gin | 性能高、生态成熟、文档完善 | 抽象层较高 | 采用 |
| Echo | 功能相近 | 社区体量略小 | 不采用 |
| Chi | 轻量 | 功能较少、需自行补齐 | 不采用 |

## ADR-005: ORM选择 GORM

- 状态：已接受
- 背景：需要快速建模与迁移能力，并支持钩子与与 Gin 集成。
- 决策：选用 GORM 作为 ORM。
- 理由：Go生态最成熟ORM、自动迁移、钩子机制、与Gin集成良好。
- 后果：数据库访问层围绕 GORM 进行抽象。

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| GORM | 生态成熟、自动迁移、钩子完善 | 抽象成本 | 采用 |
| sqlc | 轻量、高性能 | 需手写SQL | 不采用 |

## ADR-006: 前端框架选择 Vue 3 + Vben Admin

- 状态：已接受
- 背景：需要企业级后台管理前端、快速具备权限与组件体系。
- 决策：选用 Vue 3 + Vben Admin。
- 理由：企业级后台模板、TypeScript支持、Ant Design Vue组件库、开箱即用的RBAC。
- 后果：前端技术栈固定为 Vue 3 生态。

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| Vue 3 + Vben Admin | 企业级模板、TS支持、RBAC开箱即用 | 需要模板学习成本 | 采用 |
| React Admin | 生态成熟 | 学习曲线陡、自建成本高 | 不采用 |

## ADR-007: 监控数据透传而非存储

- 状态：已接受
- 背景：监控历史数据已由 VictoriaMetrics 承担。
- 决策：监控数据采用透传方式，不在 CMDB 内存储。
- 理由：VictoriaMetrics已存储历史数据、避免数据冗余、无需ClickHouse、降低运维复杂度。
- 后果：CMDB 不持久化监控时序数据，仅转发查询。

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 透传 | 避免冗余、降低运维复杂度 | 依赖外部监控系统 | 采用 |
| 本地存储 | 查询可控 | 需引入ClickHouse与运维成本 | 不采用 |

**实现要点**
- `MonitorProxy` 透传 `/api/v1/query` 和 `/api/v1/query_range`

## ADR-008: 告警系统只读集成 FlashDuty

- 状态：已接受
- 背景：N9E 已直接推送告警到 FlashDuty。
- 决策：CMDB 只读集成 FlashDuty，不进行告警推送。
- 理由：N9E已直接推送告警到FlashDuty、CMDB只需展示不需推送、避免告警链路复杂化。
- 后果：告警链路保持单向，CMDB 仅展示。

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 只读集成 | 链路简化、风险低 | 依赖外部系统 | 采用 |
| 双向推送 | 功能完整 | 复杂度高 | 不采用 |

**实现要点**
- `AlertProxy` 只读调用 FlashDuty Open API

## ADR-009: 权限控制选择 Casbin RBAC

- 状态：已接受
- 背景：需要成熟的 RBAC 方案与 Go 生态兼容。
- 决策：选用 Casbin 作为 RBAC 引擎。
- 理由：Go生态最成熟的RBAC库、支持多种访问控制模型、与Gin中间件集成简单。
- 后果：权限模型以 Casbin 策略为核心。

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| Casbin RBAC | 模型灵活、生态成熟、易集成 | 策略维护成本 | 采用 |
| 自研RBAC | 可完全定制 | 维护成本高 | 不采用 |

**角色定义**
- `admin` / `operator` / `viewer`

## ADR-010: 部署方式选择单二进制 + Go Embed

- 状态：已接受
- 背景：需要降低部署复杂度，避免额外网关与静态资源分发。
- 决策：采用单二进制 + Go Embed 部署。
- 理由：Go 1.16 embed特性将前端静态资源嵌入二进制、无需Nginx、无跨域问题、scp即可部署。
- 后果：发布物为单一可执行文件。

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 单二进制 + Go Embed | 部署简单、无跨域、无Nginx | 构建体积增加 | 采用 |
| Docker 部署 | 依赖隔离 | 运维复杂、需容器平台 | 不采用 |
